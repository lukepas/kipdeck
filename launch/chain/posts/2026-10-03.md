# Day 2: the escrow state machine

Date: 2026-10-03
Status: ready
Built in: 22a8915 (program), f6e9b7d (SDK)
Media: the state diagram below, drawn as an image. Alt text: "Bounty states: Open, Claimed, Released, Refunded, Cancelled, with who can move each step."

```text
Open --Fund (anyone)--> Open
Open --Claim (attester: the office's own PR, not a fork)--> Claimed
Claimed --Release (attester AND approver, after an admin approves)--> Released
Open/Claimed --expiry--> Refund, one funder at a time (anyone can crank) --> Refunded
Open, empty --Cancel (its creator or the approver)--> closed
```

```field name="X 1" max-chars=280
How an agent bounty moves, on a Solana program we wrote for this (native Rust, no Anchor).

Anyone funds. The office claims for the PR its own worker opened. A release needs two signatures. If nothing is released by the expiry, anyone can crank each funder's refund.
```

```field name="X 2" max-chars=280
Why two keys? The attester checks GitHub: merged by a person with write access, not a bot, not a fork. The approver signs only after an office admin presses Approve payout.

Two keys, two checks; the approver can be an admin's browser wallet. A bot merge never reaches the inbox.
```

```field name="X 3" max-chars=280
The rules live in a dependency-free Rust module. The program and the TypeScript SDK both test against one shared table of cases, and litesvm runs the built program. Every step logs an event, so payouts can be counted from the chain alone.
```

```field name="Farcaster" max-chars=320
The bounty escrow for AI coding agents, as a state machine: anyone funds, the office claims for its own (non-fork) PR, and a release needs two signatures, the attester's (a person merged it) and the approver's (an admin approved). After expiry anyone can crank refunds. Native Rust, no Anchor.
```
